# 企微会话存档 SDK 选型对比：NICEXAI/WeWorkFinanceSDK vs 官方 C SDK 直接封装

> 评估日期：2026-10-14。结论：两者底层是**同一个官方动态库**，导出数据完全一致；差异只在 Go 封装层。

## 1. NICEXAI/WeWorkFinanceSDK 的本质

**它不是纯 Go 实现，而是官方 C SDK 的 cgo 封装**：

- 仓库 `lib/` 里直接带着官方 `libWeWorkFinanceSdk_C.so`（x86-64，版本 200215，2020 年的老版本）。
- 构建约束 `//go:build linux && cgo`——**只支持 Linux + cgo**，非 Linux 直接报错。
- 数据链路：`GetChatData` 调官方 C 函数拉数据；`DecryptData` = 纯 Go 解 RSA random_key（`rsa.go`，PKCS#1 v1.5）+ 官方 C 函数 `DecryptData` 解消息体。

所以"用 Go 导出数据"这个期望要修正：**会话存档数据只能经官方 C 库拉取，不存在纯 Go 通道**。这个库并没有绕开 cgo。

## 2. 实测结果

在 arm64 环境下实测（沙箱为 ARM64 Linux）：

- 该库自带的 x86-64 `.so` 在 arm64 下链接失败（`skipping incompatible`）。
- 将其 `lib/` 替换为官方 arm64 版 SDK（20250205）后：**编译通过，`NewClient` 初始化成功**。
- 即：该库可以用，但必须自行替换对应架构的新版官方库。

## 3. 与我们的实现对比

| 维度 | NICEXAI/WeWorkFinanceSDK | 我们的实现（internal/wecom） |
|---|---|---|
| 底层 | 官方 C 动态库（cgo） | 同一个官方 C 动态库（cgo） |
| 导出数据内容 | 企微服务端原始 JSON，完全一致 | 完全一致 |
| 自带库版本 | 200215（2020 年，旧） | 20250205（新版，已内置 amd64+arm64） |
| 架构支持 | 仅自带 x86-64，arm64 需手动换库 | amd64/arm64 双架构已内置 |
| 解密 | 纯 Go 解 RSA + C 库解消息体 | 相同思路，另有纯 Go 兜底实现（crypto.go，已实测） |
| 消息结构 | 按 msgtype 类型化（message.go） | 通用 Message + Raw 原始 JSON |
| 平台 | 仅 Linux | Linux/macOS 均可（按构建标签降级） |
| 维护活跃度 | 低（个人项目） | 自控 |

## 4. 结论与建议

**数据无差异**：两边走的是同一个官方 `.so`，从企微服务端拿到的数据一字不差，不存在"导出效果"差异。

**可借鉴的点**：它的 `message.go` 对每种消息类型（text/image/file/video/会议邀请等）定义了类型化结构体，比我们的通用 Message 更细。后续做消息分类落盘时可参考其字段定义。

**建议**：保留现有自研封装（新版 SDK、双架构、可控），不引入该第三方库作为依赖——它带来的封装便利性有限，却引入了一个低维护度的外部依赖，且仍要我们自己替换新版库。

## 5. 关于"纯 Go 导出"的可行性

不可行。企微会话存档的拉取协议未公开，官方仅通过 C SDK 提供（内部封装了鉴权、传输、分片）。任何 Go 方案最终都要落到这个动态库上。我们能做的优化已全部做掉：纯 Go 实现了解密兜底、封装了 cgo 接口、内置了双架构新版库。
