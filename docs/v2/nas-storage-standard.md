# NAS 落库标准 v2

> 状态：已与需求方确认（智能纪要分类 A7 待实测）· 2026-10-30
> 配套文档：[架构设计](architecture.md) · [索引与待决事项](README.md)
> 标【待确认】的条目编号对应 README 里的 B 类待决事项。

## 0. 现状（v1）与问题

```
<root>/
└── <人名>/
    ├── 企微/
    │   ├── 群聊记录/
    │   │   ├── <会话名>.md                 # 一直追加
    │   │   └── images/<YYYY-MM-DD>/...
    │   └── <YYYY-MM-DD>/<附件>              # 文件、语音、视频等
    └── 飞书/
        ├── 云文档/...                        # 导出的文档；智能纪要也在这里（PR #23）
        └── 邮件/...                          # 目前只有附件
```

1. 根目录用**人名**（v2 保留这一点）；但名单外的人也会建目录，离职没有任何标记。
2. 未纳管的人（例如测试租户的管理员）也会有目录。
3. 单聊和群聊没有区分；会话改名就会产生新文件。
4. 会话文件一直追加，越来越大，FastGPT 每次都要重新处理整个文件。
5. 离职状态、数据来源、同步时间这些元数据在目录里看不到，排查只能查 SQLite。

## 1. 顶层目录

```
<root>/
├── _system/                           # adapter 自用，不通过 API 文件库暴露
│   ├── README.md                      # 本标准的简版说明
│   ├── roster-snapshot.json           # 最近一次名单快照（不含手机号等敏感字段）
│   └── unmanaged/                     # 迁移时不在名单内的 v1 目录，待人工处理
├── <人名>/                            # 在职员工，例：Tom 张三
└── <人名>_离职/                       # 离职员工：原目录原地改名，只读
```

- **目录名就是人名，不带任何 ID**（已确认 B1，2026-10-29）。根目录下直接是员工目录，不分 `在职/` `离职/`。
- **员工 ID**：内部仍用**企微 `user_id`**（已确认）关联名单、token 和数据库归属，只是不出现在目录名里。adapter 在 SQLite 里记"员工 ID → 目录名"。
- **重名**（已确认 B12）：名单里两个在职员工同名时，由名单维护人改写其中一人的姓名（例如 `张三(销售)`）；adapter 发现重名时不为这两人建目录、不同步并告警，不自动加后缀、不覆盖。
- **员工改名**（已确认 A17）：**不改目录名**，目录名在首次建目录时记入 SQLite。目录一改名，里面所有文件的 id 都会变，FastGPT 要整体重新向量化。新名字只写进 `_profile.md`。
- **离职**（已确认 B2，2026-10-29）：把员工目录**原地改名为 `<人名>_离职`**，写入 `_离职说明.md`（姓名、员工 ID、离职日期、归档时间），之后 adapter 不再写入。
  - 离职后知识库也停用，所以改名导致 id 变化没有影响。
  - `<人名>_离职` 已存在（同名的人先后离职）时，改名为 `<人名>_离职_<YYYYMMDD>`。
  - 被移出名单（不是离职）的人：只吊销 token，目录不改名。
  - 复职按新员工处理，新建 `<人名>/`；`<人名>_离职` 保留不动。
- 只有**名单内在职员工**有目录；外部联系人和未纳管员工不建目录。授权了飞书但不在名单内的人也不拉取（已确认）。

## 2. 员工目录结构

```
<人名>/
├── _profile.md                        # 姓名、部门、企微/飞书账号、状态、最后同步时间
├── 企业微信/
│   ├── 单聊/<对方名>/
│   │   └── <YYYY-MM>/<YYYY-MM-DD>.md  # 按天分卷，按月归目录
│   ├── 群聊/<群名>/
│   │   └── <YYYY-MM>/<YYYY-MM-DD>.md
│   └── 附件/<YYYY-MM>/<YYYYMMDD-HHMMSS>_<原文件名>
└── 飞书/
    ├── 云盘/
    │   ├── 我的文件夹/<原目录结构>/<文档名>.<ext>
    │   ├── 共享文件夹/<文件夹名>/<原目录结构>/<文档名>.<ext>
    │   └── 与我共享/<文档名>.<ext>        # 单独分享的单篇文档（A15）
    ├── 智能纪要/
    │   ├── 归我所有/<YYYY-MM>/<YYYYMMDD>_<标题>.<ext>
    │   ├── 我参与的/<YYYY-MM>/...
    │   └── 与我共享/<YYYY-MM>/...
    └── 邮件/
        ├── 收件箱/<YYYY-MM>/<YYYYMMDD-HHMMSS>_<主题>/   # 收到的邮件（含已归档、自建文件夹里的）
        │   ├── 正文.html
        │   └── <附件原文件名>
        └── 已发送/<YYYY-MM>/<YYYYMMDD-HHMMSS>_<主题>/   # 本人发出的邮件，结构同上
```

### 2.1 企业微信

- **单聊和群聊分开存放**。会话目录名**不带 ID**，直接用群名 / 对方名（已确认 B3）。群改名后新消息进新名字的目录，旧目录保留；同名的两个会话会落进同一个目录。
- **会话按天分卷**（已确认 B4）：`<YYYY-MM>/<YYYY-MM-DD>.md`，取代 v1 的单文件一直追加。有新消息时 FastGPT 只需重新拉取当天这一卷；按月建子目录，避免单个目录文件过多。
- **附件和图片**统一放在 `附件/<YYYY-MM>/`，会话 Markdown 里用相对路径引用，不再单独设 `images/` 目录。

### 2.2 飞书

- 同步范围已与需求方确认：
  - 云盘：只含"我的文件夹""共享文件夹"两棵树；
  - 智能纪要：分三类；
  - 邮件：收到的和已发送的邮件都存，正文和附件一起存（已确认 A13，2026-10-30 改）；
  - 知识库（含"我的文档库"）、妙记逐字稿不在范围内。
- **只保留当前状态**：源端删除，NAS 跟着删除；源端改名或移动，NAS 跟着移动；文件 id 随之变化，FastGPT 重新索引（已确认，可接受）。
- **云盘分"我的文件夹 / 共享文件夹 / 与我共享"三个区**：前两个和飞书界面一致；`与我共享/` 放不在任何共享文件夹里的单篇分享文档（A15）。FastGPT 回答时能说清来源。
- **智能纪要**：
  - 一篇纪要同时属于多类时只放一处（已确认 B5），优先级：归我所有 > 我参与的 > 与我共享。
  - B6（已确认）：按本标准的分类和命名归档。格式沿用 `.docx` 导出（已确认）；妙记逐字稿不同步（已确认 A6）。
- **邮件一封一个目录**：正文用飞书能导出的格式存为 `正文.html`（开头写明发件人、收件人、抄送、时间和主题，内联图片嵌入），附件保持原格式，和正文放在同一目录（已确认 B11）。

## 3. 文件命名

| 规则 | 说明 |
|---|---|
| 非法字符 | `/ \ : * ? " < > \|` 及控制字符替换为 `_` |
| 长度 | 文件名（不含扩展名）最长 120 个字符；超出时截断，并追加 `~<哈希前6位>` |
| 同名冲突 | 同一目录下重名时**直接覆盖**（已确认，2026-10-29） |
| 时间 | 统一使用北京时间（UTC+8），格式 `YYYYMMDD-HHMMSS` / `YYYY-MM` |
| 编码 | UTF-8；Markdown 统一 LF 换行 |
| 敏感信息 | 文件名和路径中不出现手机号、身份证号等 |

## 4. 会话 Markdown 格式

```markdown
---
source: wecom
chat_type: group            # single | group
chat_id: wrxxxxxxxx
chat_name: 产品周会
date: 2026-10-29
participants: [王五, 张三, 外部:李四@某公司]
---

## 2026-10-29

**10:03:12 王五**：今天的议程……
**10:05:40 张三**：[文件] 需求文档.pdf → [附件](../../附件/2026-10/20261029-100540_需求文档.pdf)
**10:06:02 外部:李四@某公司**：[图片] ![](../../附件/2026-10/20261029-100602_img.jpg)
```

- 每条消息占一行，带时间和发送人；每天一个二级标题，方便 FastGPT 分块。
- 外部联系人写成 `外部:<名称>@<企业>`；拿不到名称时写 `外部:<ID后6位>`。
- 撤回的消息保留原文，并标注"（已撤回）"（已确认 B7）。
- 无法解析的消息类型写成 `[不支持的消息类型: xxx]`，不丢行。

## 5. 元数据

- 每个落盘文件在 SQLite 的 `files` 表里记一条：来源、源 ID、所属员工、内容哈希、源端修改时间、同步时间、权限快照、API 文件库 id。
- NAS 上**不放** sidecar 隐藏文件，免得被 FastGPT 当成内容读进去。现有的 `.meta.json` 迁移进 SQLite。
- `_profile.md` 是员工目录里唯一给人看的元数据文件。

## 6. 写入与删除规则

| 场景 | 行为 |
|---|---|
| 企微新消息 | 追加到当天卷；按"msgid × 员工"去重，重放幂等 |
| 飞书文档更新 | 内容哈希变化才覆盖写 |
| 飞书文档删除 / 失去权限 | **直接删除**该授权人目录下的副本，不留档（已确认）；单轮删除比例过高（当前为 50%）时熔断并告警 |
| 飞书文档移动 / 改名 | NAS 跟着移动 / 改名，FastGPT 重新索引（已确认） |
| 员工离职 | 目录改名为 `<人名>_离职`，停止写入，永久保留 |
| 员工移出名单 | 吊销 token，停止写入，目录不改名 |
| 未纳管人员 | 不建目录，不落副本 |

## 7. 权限、容量与安全

- NAS 目录权限：只有 adapter 的服务账号能访问，员工本人不直接访问 NAS（已确认 B8）。
- 企微首次全量拉取前先评估容量：按 seq 范围抽样，估算附件体积。

## 8. 从 v1 迁移

1. 停服，导出 v1 的目录清单。
2. 员工目录名不变（仍是 `<人名>/`）；不在名单内的目录移到 `_system/unmanaged/` 等人工处理，不删除；名单里已离职的人，目录改名为 `<人名>_离职`。
3. 企微：v1 的 `<会话>.md` 没法可靠地拆成月卷，倾向**清空企微目录，从 seq=0 重新拉取**，这也符合"企微从头全量拉"的要求。
4. 飞书：清空后按当前状态重新同步。
5. FastGPT：旧的推送型知识库由 FastGPT 侧清理；FastGPT 侧按新目录和 adapter 提供的 token 清单配置 API 文件库。

迁移已确认（B9）：企微、飞书都按新标准重拉，不保留 v1 文件。
