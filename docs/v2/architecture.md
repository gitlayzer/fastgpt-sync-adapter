# fastgpt-sync-adapter 架构设计 v2

> 状态：草案 · 2026-10-29
> 角色：架构设计与验收由架构负责，实现按任务拆分后交由 pi 执行
> 配套文档：[NAS 落库标准](nas-storage-standard.md) · [索引与待决事项](README.md)

## 1. 背景与目标

为每位在职员工建一个**个人 AI 知识库**：

1. 自动汇集他在企业微信、飞书里**有权看到**的工作数据；
2. 归档到群晖 NAS；
3. FastGPT 通过 **API 文件库**从 adapter 拉取。

文件始终存在 NAS 上。adapter **只负责把数据按人整理到 NAS，并通过 API 文件库接口按员工隔离地提供文件**；FastGPT 侧的知识库创建、工作流和飞书机器人都不在 adapter 范围内。

v2 相对 v1 的核心变化：

| 维度 | v1（现状） | v2（目标） |
|---|---|---|
| FastGPT 对接 | adapter 自动建知识库并主动推送文件 | **FastGPT API 文件库主动拉取**；adapter 不再创建、管理知识库，只按员工隔离提供文件接口 |
| 飞书应用 | 读名单、同步各用一个应用，open_id 跨应用不通 | **统一为一个同步应用** |
| 变更感知 | 定时全量扫描（企微 1 分钟、飞书 5 分钟） | **事件驱动 + 定时对账兜底** |
| 副本归属 | 文档所有者和可见人都落副本（含未纳管的人） | **只给名单内在职员工落副本** |
| 离职 | 不处理 | **目录改名为 `<人名>_离职`、停止同步、吊销 token、旧数据永久保留** |
| 权限一致性 | 等下一轮全量扫描 | **常见变更 1～2 分钟内对齐**，继承 / 群组类靠对账 |
| 可靠性 | 写入失败可能丢消息 | 失败保留游标重试 + 死信（PR #22） |

## 2. 设计原则

1. **NAS 是唯一可信源**：所有数据先落 NAS。FastGPT 从 NAS 拉取，是派生物，可以随时重建。
2. **权限即副本**：员工目录里有什么，就等于他有权看什么。权限变化 = 在他目录里增删文件。
3. **只服务纳管员工**：名单内且在职的人才有个人目录和知识库。外部联系人、未纳管的人只作为参与者出现在内容里。
4. **不丢、不误删**：写入失败不推进游标；删除有熔断；离职只冻结不删除。
5. **敏感信息不出本地**：凭据、名单、数据库文件不进仓库；日志脱敏。
6. **实时是优化，对账是保证**：事件只负责加速，正确性由周期对账兜底，丢一个事件不影响最终一致。

## 3. 总体架构

```
            ┌──────────── 事件（近实时）─────────────┐
            │  飞书长连接事件 / 企微新消息回调          │
            │  通讯录变更（入职 / 离职）                │
            ▼                                         │
 ┌────────────────────┐   ┌─────────────────┐   ┌────────────────┐
 │ 连接器              │──▶│ 归属与权限计算   │──▶│ NAS Sink       │──▶ 群晖 NAS（可信源）
 │ 企微会话存档 / 飞书  │   │ Identity + ACL  │   │ 按人落盘 / 删除 │          │
 └────────────────────┘   └─────────────────┘   └────────────────┘          │
            ▲                                                                ▼
            │ 周期对账（全量扫描兜底）                          ┌─────────────────────────┐
            └──────────────────────────────────────────────────│ API 文件库服务（adapter）│
                                                                │ 按员工 token 隔离目录    │
                                                                └──────┬────────▲─────────┘
                                                            拉取文件    │        │ （可选）目录变化后提醒同步
                                                                ┌──────▼────────┴─────────┐
                                                                │ FastGPT API 文件库       │
                                                                │ 由 FastGPT 侧创建和配置  │
                                                                └─────────────────────────┘
```

沿用 v1 的 Engine / Connector / Sink / Task 结构，新增三个模块：

- **EventBus**：接收飞书长连接事件和企微回调，转换为"重扫某人 / 重扫某文档 / 拉企微新消息"的内部任务，去抖后交给连接器。
- **Lifecycle（人员生命周期）**：处理入职和离职，维护员工状态，驱动 NAS 目录改名为 `<人名>_离职` 和文件服务 token 吊销。
- **Reconciler（对账）**：保留现有的定时全量扫描，周期放长到 30～60 分钟，专门修正事件漏掉的变化。

## 4. 身份与人员生命周期

### 4.1 统一飞书应用

- 同步应用直接读取名单多维表格：给应用开通 `bitable:app:readonly`，并在名单表的"… → 添加文档应用"里加入同步应用。
- 用同步应用读取名单的"人员"字段时，返回的就是同步应用自己的 open_id。不再需要人工维护"飞书open_id"列，跨应用 ID 不通的问题随之消失。
- 备选方案：如果无法统一，名单改存 `user_id`（租户内唯一）或 `union_id`（同一开发者主体内唯一），由 adapter 统一换算成同步应用的 open_id。
- **已验证**（2026-10-29，测试租户，待决 A2）：同步应用能读取名单表，人员字段返回的 open_id 与员工 OAuth 授权得到的一致。

### 4.1a 员工 ID（已确认，2026-10-29）

- 员工 ID 统一用**企微 `user_id`**。名单多维表格以企微 `user_id` 为键，查出这个人对应的飞书身份。
- 文件服务 token、SQLite 里的归属都用这个 ID；NAS 目录名只用人名，不带 ID。
- 没有企微账号、只有飞书账号的员工，员工 ID 用 `feishu:<open_id>`（已确认 A16）。
- 授权了飞书但不在名单内的人：**不拉取**，以名单为准。

### 4.2 员工状态

`identities` 表新增状态字段：

| 状态 | 含义 | 同步行为 |
|---|---|---|
| `active` | 名单内在职 | 正常同步、落副本，通过 API 文件库提供给 FastGPT |
| `offboarded` | 已离职 | **停止一切同步**；NAS 目录改名为 `<人名>_离职`、永久保留；吊销文件服务 token |
| `removed` | 已从名单中删除 | 停止同步，吊销 token；**不改目录名**（可能是误删，恢复后继续用原目录） |

- 状态来源：名单表的"状态"列为主（另有"离职日期"列），飞书 / 企微通讯录离职事件用来加速。
- **纳管员工** = 状态 `active` + 姓名非空 + 与其他在职员工不重名。重名的两人都不纳管，并告警（B12）。
- **目录名固定**（已确认 A17）：第一次被判定为纳管时，取当时的姓名作为目录名记入 SQLite，之后名单改名不换目录。
- 离职是单向的；复职按新员工处理，恢复为 `active`，目录名重新取当时的姓名，新建 `<人名>/`。
- 名单某一行写库失败时，本轮不做"移出名单"判定，避免误吊销 token。

### 4.3 副本归属规则（修正 v1）

- **飞书**：**谁授权就拉谁，只落授权人本人目录**。用授权人自己的 token 拉取他能看到的内容，他目录里的东西就是他在飞书里能看到的东西；不再像 v1 那样给文档的其他协作者分发副本（已确认 A12）。单独分享给他（或他所在群 / 部门）的单篇文档，由他本人按创建人搜索发现；搜索结果不保证完整，所以不作删除依据，删除前逐篇用他的 token 确认已无权限（已确认 A15）。
- **企微**：一条消息给"发送者 + 接收者 / 群成员"与"在职纳管员工"的**交集**落副本。
- 外部联系人、未纳管员工、已离职员工**不建目录、不落副本**，只出现在内容里。

## 5. 数据源同步

### 5.1 企业微信（会话内容存档）

- **首次上线从 seq=0 全量拉取**，之后增量拉取，游标是 seq。
- 写入失败时保留游标、整批重试；连续 5 轮失败后转入死信表，再推进游标（PR #22 已实现）。
- 近实时：接入会话存档的"新消息通知"回调，收到通知立即拉一次，定时拉取兜底。
- 企微消息没有事后的权限变化，只需处理人员的入职和离职。
- 外部联系人显示名：需要在企微后台给应用开通客户联系权限，当前报错 48002。
- 出口 IP 白名单：**已加白**，2026-10-29 实测拉取正常。

### 5.2 飞书

**谁授权就拉谁**：员工完成飞书 OAuth 授权后，adapter 用他本人的身份拉取，只同步当前状态，不保留历史版本。没授权的人不拉；授权失效或撤销后停止拉取，已有数据保留（待决 A11）。

每个授权人的同步范围（已与需求方确认，2026-10-29）：

| 类别 | 范围 | 当前进度 | v2 待做 |
|---|---|---|---|
| 云盘 | "我的文件夹"和"共享文件夹"下，所有归我所有、以及与我共享的文档（递归） | 我的文件夹递归 ✅；共享文件夹按创建人搜索发现（PR #21）✅ | 单篇分享：搜索只收文件夹，单篇靠协作者分发 → 改为本人搜索发现（A15）。知识库（含"我的文档库"）已加开关 `wiki_enabled`，默认关闭；关键字搜索已默认关闭（A6） |
| 智能纪要 | 归我所有、我参与的、与我共享 | 纪要文档：按关键词"智能纪要"搜索，参会人也能找到，导出为 .docx（PR #23）✅；妙记逐字稿走 `minutes/search`（不在需求内，关掉，A6） | 给每条纪要标出所属类别（"我参与的"和"与我共享"如何区分，待实测）；按 NAS 标准分目录（待决 A7） |
| 飞书邮件 | **收到的和已发送的**邮件：正文 + 附件 | PR #24：收件箱、已发送、自建文件夹翻页拉全；正文存 `.html`（内联图片嵌入）+ 全部非内联附件；已处理记录入 SQLite，写入成功才记；按 RFC 邮件 ID 去重；每天核对一次，所有拷贝都已删除时 NAS 跟着删（A14） | 收件、已发送分目录存放；一封一个目录，正文 `.html`（B11，随 P2） |

- 三类数据都只落授权人本人目录。同一份文档或同一封邮件，多个授权人都能看到时，各自目录里各存一份。
- **近实时**：通过长连接（WebSocket）订阅事件，不需要公网回调地址。
  - 文档协作者增删、文档删除或移入回收站 → 重新检查受影响的授权人还能不能看到，增删他们目录里的副本。
  - 文档内容更新 → 重新导出。
  - 通讯录离职 → 交给 Lifecycle。
  - 云文档事件需要按文件订阅，首次发现文档时登记订阅。
- **事件拿不到的变化靠对账**：父文件夹的权限继承、群和部门的成员变动、"组织内获得链接可读"类分享。

#### 权限变化处理（已与需求方确认，2026-10-29）

原则：**授权人的 NAS 目录 = 他在飞书里当前能看到的内容。**

| 变化 | 处理 | 发现方式 |
|---|---|---|
| 新分享给他 / 加入共享文件夹 | 拉进他的目录 | 事件 + 定时扫描 |
| 失去访问权（移出协作者、移出群 / 部门、父文件夹权限收回等任何途径） | **直接删除**他目录里的副本，不留档；只删他那份，不影响别人 | 事件 + 定时扫描；继承 / 群组类只能靠对账 |
| 仍能通过其他途径访问（父文件夹、群、部门） | 不删 | — |
| 阅读 / 编辑等权限级别变化 | 不处理，只关心能不能看 | — |
| 文档移动、改名、所有者变更 | NAS 跟着移动 / 改名；FastGPT 视为删旧建新，**重新索引**（可接受） | 定时扫描 |
| 改成"组织内获得链接可阅读"但未单独授权 | 不拉（搜索接口不返回，PR #23 实测；文件夹列表是否列出待实测） | — |

删除保护：

- 该授权人本轮扫描有任何接口错误 → 本轮不做删除判断。
- 单轮删除超过阈值 → 熔断并告警。
- token 失效或被撤销 ≠ 失去权限 → 只停止同步，不删数据（待决 A11）。

已知窗口：NAS 删除后，FastGPT 要等下一次同步才移除；在此之前已向量化的内容仍可能被检索到（见 §7.3、待决 A9 / A10）。

### 5.3 一致性目标

| 变化类型 | 目标延迟 | 机制 |
|---|---|---|
| 企微新消息 | ≤ 1 分钟 | 回调 + 定时兜底 |
| 飞书文档新增 / 修改 / 删除 | 1～2 分钟 | 事件 |
| 飞书显式协作者增删 | 1～2 分钟 | 事件 |
| 继承 / 群组 / 链接分享导致的权限变化 | ≤ 1 小时 | 对账 |
| 离职 | 1～2 分钟 | 通讯录事件 + 名单刷新 |
| FastGPT 可检索到 | 上述延迟 + FastGPT 拉取周期 + 向量化耗时 | FastGPT 侧同步机制（§7.3） |

> 表中前五行的延迟只保证到 **NAS 和文件服务**这一层，之后由 FastGPT 侧决定。

## 6. NAS 落库

详见 [NAS 落库标准](nas-storage-standard.md)。架构层面的约束：

- 每个在职纳管员工一个根目录，目录内容就是他的权限范围。
- 员工目录名就是人名，不带 ID，直接放在根目录下。
- 离职员工的目录原地改名为 `<人名>_离职`、冻结、永久保留。
- 所有写入幂等，重放不产生重复内容。
- 每次删除都必须能追溯到源端删除或权限撤销。
- **路径尽量稳定**：API 文件库的文件 id 由路径算出，路径变了 FastGPT 就要重新向量化（§7.2）。

## 7. 与 FastGPT 的对接

> **方向调整（2026-10-29）**：由"adapter 自动建知识库并主动推送"改为"**FastGPT API 文件库主动拉取**"。
>
> - 文件始终存在 NAS 上。adapter 只负责整理好 NAS，并通过 API 文件库接口把文件暴露给 FastGPT。接口是 `/v1/file/list`、`content`、`read`、`detail`、`download`，在现有的 `internal/server` 和 `internal/nasstore` 基础上改造。
> - adapter **不再创建、管理 FastGPT 知识库**，也不负责工作流和飞书机器人；这些由 FastGPT 侧负责。
> - 推送 Sink（`internal/sink/fastgpt`）下线；按 FastGPT 用户列表在 NAS 建目录的逻辑（`ensureUserDirs`）也下线，员工目录只由名单决定。

### 7.1 按员工隔离的文件服务（token 方案已确认，2026-10-29）

**一个员工一个 token；token 本身决定能看哪个目录，FastGPT 侧不用配根目录，配了也越不出去。**

**token 与存储**

- 格式：`fsa_` 前缀 + 32 字节随机数（base64url）。不由员工 ID 推导，可单独吊销。
- SQLite 表 `api_tokens`：只存 SHA-256 哈希，不存明文。字段：token 哈希、前缀（便于辨认）、员工 ID、状态（active / revoked）、签发时间、过期时间（轮换宽限用）、最近使用时间、吊销时间。
- token 绑定**员工 ID**，不绑定目录路径：员工改名、离职目录改名都不用重发，服务端每次按员工 ID 找他当前的根目录。
- **明文只出现一次**（已确认）：签发或轮换时输出一次，之后系统里查不到；丢了就轮换。

**请求处理**

1. `Authorization: Bearer <token>` → 员工 → 根目录；无效或已吊销返回 401。
2. `parentId` 为空时返回**该员工根目录**的内容，而不是 NAS 根目录。
3. 所有带 id 的请求（list / content / read / detail / download）先经 `id → 路径` 解析，路径不在根目录下返回 404（不提示"无权限"，不暴露文件是否存在）。
4. 搜索只在该员工根目录内进行。
5. 下载链接不带 token，改为签名链接：`文件 id + 员工 ID + 过期时间`，用服务端密钥 HMAC 签名，默认 10 分钟有效。

**管理员全量 token（已确认保留）**

- 单独配置一个管理员 token，可看整个 NAS，用于运维排查和现有的目录浏览页面。
- 默认关闭；开启后只接受来自内网 / 配置白名单地址的请求。不交给 FastGPT 使用。

**签发与交付**

- 名单新增在职员工时自动签发，写入一份**待交付清单**（姓名、员工 ID、baseUrl、token），交给 FastGPT 管理员配置 API 文件库。清单是敏感文件，不进仓库，交付后删除。
- 命令行：`adapter token issue|list|rotate|revoke`。`list` 只显示前缀和状态。
- 轮换：新旧 token 并存 24 小时，之后旧 token 自动失效。

**生命周期**

| 事件 | token |
|---|---|
| 新员工进入名单 | 自动签发，进入待交付清单 |
| 员工离职 | 自动吊销；NAS 数据保留 |
| 飞书授权失效 | **不吊销**，已有数据仍可拉取，只是不再更新（A11） |
| token 泄露或丢失 | 单独轮换该员工的 token |

### 7.2 文件 ID 与性能

- 现状 `id = sha1(相对路径)`：文件改名或移动后 id 会变，FastGPT 会当成删掉旧文件、新增一个文件，需要重新向量化。
- 现状 `Get(id)` 要逐层遍历 NAS 反查路径，文件一多就慢。v2 用 SQLite 维护 `id → 路径` 索引，NAS Sink 写入和删除时同步更新。

### 7.3 同步时效（拉模式的代价）

- FastGPT 何时发现新增、变更、删除，取决于 FastGPT 侧的同步机制（手动同步、定时同步）。§5.3 前五行的延迟只保证到 NAS 和文件服务。
- **待验证（待决 A9）**：FastGPT API 文件库能不能自动发现新增文件、处理已删除的文件。验证计划见 §7.3.1。

#### 7.3.1 FastGPT 同步行为验证计划（A9，待排期）

**做法**：不看 FastGPT 源码猜，而是用 adapter 的访问日志观察。文件服务每次被调用都会记录员工 ID、接口、文件 id，能直接看出 FastGPT 何时来拉、拉了什么。必要时再对照 FastGPT 源码确认原因。

- FastGPT 定时同步能覆盖新增、变更、删除，且周期可接受：adapter 不调用 FastGPT。
- 否则：adapter 在员工目录变化后调用 FastGPT 的同步接口，这需要在配置里加 FastGPT 的 API Key 和每个员工的知识库 ID。

**执行**：V2–V7 需要在 FastGPT 界面上操作，由有 FastGPT 账号的人做；adapter 侧准备测试目录和 token、看访问日志、整理结论。V8 先查文档。
- 可选增强（待决 A10）：如果 FastGPT 的定时同步太慢，adapter 可以在员工目录变化后调用 FastGPT 的同步接口提醒它来拉；这需要 FastGPT 的 API Key 和知识库 ID。默认不做，adapter 不调用 FastGPT。

### 7.4 安全

- 现在的预览 / 下载链接直接带长期 token，可能进到 FastGPT 或代理的日志里。改为**短期签名链接**：文件 id + 过期时间 + 签名。
- 文件服务的外部地址只允许 FastGPT 的出口访问，走内网或白名单。
